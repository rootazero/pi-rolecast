# v0.6.0 optimization roadmap — governance-layer redesign

Status: **in progress**. Target release: **v0.6.0**.

This document is the master plan for the v0.6.0 rewrite. It is **not** a
spec — the live spec lives in `src/profile_loader.ts` (schema), the role
pack files (semantics), and `tests/unit/*.ts` (behaviour). When those move,
this document lags. When in doubt, trust the code.

## Why

Reference: [@Akagilnc/ak-pi-workflow-roles](https://github.com/Akagilnc/ak-pi-workflow-roles).
Their v3 ("role factory") design drops the central orchestrator
(ADR-0010), adds typed submission contracts per role (ADR-0003), layers
generic law + host overlay into soul files (ADR-0005), narrows the judge
toolset (ADR-0008), explicitly refuses to impose retry brakes on audit
rejections (ADR-0007), and gives workers explicit phase inputs (ADR-0034).

pi-rolecast v0.5.x is a thin dispatcher: profile binds role → alias →
model, sync writes the binding into project-local agent files, pi-subagents
fires the role via @handle or Agent tool. Almost everything else is the
parent session's responsibility. That minimalism is a strength, but it
also means role packs can drift on:

- **Output shape** — every role emits freeform text. Reviewers sometimes
  forget the verdict line. Testers sometimes forget the file:line format.
- **Tool access** — auditor and reviewer currently carry Edit/Write. They
  shouldn't.
- **Soul duplication** — every role-pack file repeats "honour non-negotiables",
  "do not commit unless asked", "respect file boundaries". That's generic
  law, not role-specific guidance.
- **Audit gates** — the framework's only concept of audit is the
  `coding-reviewer` role. There's no separation between "primary verdict"
  and "adversarial cross-check" and "evidence-taking".
- **Composition** — `coding-orchestrator` is supposed to be the dispatcher,
  but its system prompt is informal. ak's experience: the caller should
  compose, the package should make each role good in isolation.

This version takes those lessons seriously without abandoning the
profile-driven model that makes pi-rolecast different from a hand-rolled
agent roster.

## What changes (one-screen summary)

### A 套 — framework mechanisms (no role-pack changes required to use them)

| # | Mechanism | New surface | Where enforced |
|---|---|---|---|
| A1 | Output contract | `profile.contracts.<role>: <jsonSchema>` | `scaffolder validate` only (per user decision) |
| A2 | Toolset narrowing | role frontmatter `allowed_tools:` | `extension` `tool_call` hook (sets `input.allowed_tools` if Agent tool accepts; otherwise documented only) |
| A3 | Soul layering | `souls/<group>/_common.md` referenced by each role | `sync_settings` prepends soul to project-local `.pi/agents/*.md` body |
| A4 | Audit retry policy | `profile.escalation.audit_max_resubmits` (default `null` = unbounded, ADR-0007) | `scaffolder validate` + `gate_runner` (when audit phase configured) |
| A5 | Bash seatbelt | role frontmatter `forbidden_bash_patterns:` (literal substrings) | `sync_settings` writes the patterns into the role's body; framework does not enforce (ADR-0008 "seatbelt 不防坏，只是防呆") |

### B 套 — role-pack changes (templates + role files)

| # | Change | Old | New |
|---|---|---|---|
| B1 | Audit triad | `coding-reviewer` | `coding-judge` (verdict) + `coding-countersign` (adversarial) + `coding-notary` (evidence); `coding-secretariat` (audit log recorder) optional |
| B2 | Worker split | `coding-implementer` | `coding-coder` (plan + apply phases, ADR-0034) + `coding-fixer` (finalization phase) |

### C 套 — identity / naming

| # | Change | Old | New |
|---|---|---|---|
| C1 | Orchestrator deprecation | `coding-orchestrator` (active) | `coding-orchestrator` (DEPRECATED, redirect: caller composes via Agent tool). Removed in v0.7.0. |
| C2 | Naming alignment | `coding-docs` | `coding-diarist` (ak semantics: "records findings"). Other names stay — `coding-architect`, `coding-planner`, `coding-tester`, `coding-mapper`, `coding-profiler`, `coding-auditor`, `coding-canary` are clearer than ak's `gleaner-left` / `doctor` / `inspector`. |

### Migration shims

All old role names resolve via `LEGACY_ROLE_ALIASES` to the new role(s).
`validate` prints a deprecation `WARN` per old name but does not block.
v0.7.0 removes the shims.

| Old binding key | Resolves to |
|---|---|
| `coding-reviewer` | `coding-judge` |
| `coding-implementer` | `coding-coder` |
| `coding-docs` | `coding-diarist` |
| `coding-orchestrator` | **WARN: removed** — caller should compose via Agent tool directly |

## Detailed design

### A1 — Output contracts

```yaml
# .pi/rolecast.yaml
contracts:
  coding-judge:
    type: object
    required: [verdict, findings]
    properties:
      verdict:
        type: string
        enum: [approve, request_changes, reject]
      findings:
        type: array
        items:
          type: object
          required: [file, line, severity, message]
          properties:
            file: {type: string}
            line: {type: integer}
            severity: {enum: [error, warning, nit]}
            message: {type: string}
```

- New module `src/contracts.ts` exports `validateContract(schema, payload)`
  with a deliberately tiny JSON-Schema subset: `type`, `required`,
  `properties`, `enum`, `items`, `additionalProperties`. ~80 lines.
- `profile_loader.ts` parses `contracts` as `Record<string, unknown>`,
  does not enforce shape at load time.
- `scaffolder.ts::validateProfile` walks every `<role>` in `contracts`,
  calls `validateContractSchema(schema)` (a stricter variant — schema
  must itself be a valid JSON Schema). Reject with `INVALID: contracts.<role>: <reason>`.
- **No runtime enforcement.** Per user decision: contracts are
  documentation + scaffold-time validation only. Roles can still produce
  freeform text. Future v0.7.x can promote to a soft warning at dispatch
  if the role output fails a parser pass.

### A2 — Toolset narrowing

Role frontmatter:

```yaml
---
name: coding-judge
allowed_tools: [read, bash]
forbidden_bash_patterns: []
---
```

`extension.ts` `tool_call` handler reads the cached binding, loads the
role file from `role-packs/`, reads `allowed_tools`, and:

1. If `Agent` tool accepts an `allowed_tools` parameter (it currently does
   not — see pi-subagents docs), inject it.
2. Otherwise: append a "**Tool restrictions for this role**" block to the
   system prompt before injecting the model:

   ```
   You are the coding-judge role. Your allowed tools for this call are:
   read, bash. Do not use edit, write, or any tool not in the list above.
   If you find a tool you need is missing, write a findings entry asking
   the caller to dispatch a different role.
   ```

`sync_settings.ts::syncSettings` also pre-bakes the allowed_tools list
into the project-local `.pi/agents/coding-judge.md` body so the role sees
it even on Path B (@handle dispatch) which doesn't go through the
extension's tool_call handler.

**Default policy** (when `allowed_tools` is absent): all tools allowed —
backward-compatible.

### A3 — Soul layering

```
souls/
  coding/
    _common.md       # 通用执法 + 通用取证法源
role-packs/
  coding/
    coding-architect.md   # 顶部声明 Soul 引用，移除重复段落
    coding-coder.md       # 同上
    ...
```

`_common.md` content (initial draft):

```markdown
# Coding-group soul — generic law + evidence rules

## Universal law (apply to every coding-* role)

1. **Honour `non_negotiables.forbidden_patterns`.** No exceptions.
2. **Honour `non_negotiables.scope_constraints`.** Stay inside the contract.
3. **Honour project gates.** `compile`, `lint`, `test` must pass before
   you report "done". If a gate fails, fix the cause; do not silence.
4. **Do not commit** unless the user asked. Working tree changes are fine.
5. **Channel trust.** If a step went through an `unverified` channel,
   surface it; do not silently launder the result.

## Universal evidence (audit-ready roles must collect)

- Every claim that depends on file content must cite `file:line`.
- Every claim about external behaviour must cite the command + output.
- Every claim about prior work must cite the commit SHA or PR number.

## Universal output shape

- Lead with the verdict / status / decision.
- Then the evidence.
- Then the proposed next step.
```

Role files declare their dependency:

```markdown
---
name: coding-architect
soul: ../souls/coding/_common.md
---
```

`sync_settings.ts::syncSettings` reads the role's `soul:` field, loads
the file, prepends it to the role body when writing `.pi/agents/<role>.md`.
If `soul:` is absent, behaviour is unchanged (backward-compatible).

### A4 — Audit retry policy

`profile_loader.ts` adds `audit_max_resubmits?: number | null` to
`Escalation`. Default `null` (unbounded) — matches ADR-0007.

`gate_runner.ts` audit-phase branch: when a gate named `audit*` (regex)
fails, read `audit_max_resubmits`. If `null`, retry until gate passes or
external abort. If number, abort after N attempts with a clear log line.

v0.6.0 does **not** add an `audit` gate phase by default — that's a v0.7.x
candidate. A4 just plumbs the field. v0.5.x profiles that omit the field
are unaffected.

### A5 — Bash seatbelt (literal substrings, ADR-0008)

Role frontmatter:

```yaml
forbidden_bash_patterns:
  - rm -rf
  - git reset --hard
  - git clean
  - git checkout --
```

`sync_settings.ts` writes a "**Bash seatbelt**" block into the role body:

```
You have a literal-substring bash seatbelt. The following command patterns
are blocked at the policy layer (you will be re-prompted if you emit them):

- "rm -rf"
- "git reset --hard"
- "git clean"
- "git checkout --"

If you genuinely need one of these, write a findings entry explaining
why and ask the caller to run it out-of-band. Do not paraphrase or
encode the same effect via different syntax — the policy is literal.
```

No framework-level bash hook (per ADR-0008: "seatbelt 不防坏"). The
seatbelt is documentation that the role's prompt will surface every
dispatch.

### B1 — Audit triad

`role-packs/coding/coding-judge.md`:

```markdown
---
name: coding-judge
soul: ../souls/coding/_common.md
allowed_tools: [read, bash]
output_contract: review-verdict
triggers: [review, judge, is this mergeable]
---
# Judge (审刑院)

You are the **primary verdict seat**. You check both code quality and
non-negotiables compliance. Your output shape is governed by the
`review-verdict` contract — do not deviate from it.

You are NOT the adversarial cross-check (that's `coding-countersign`).
You are NOT the evidence-taker (that's `coding-notary`). Stay in your lane.
```

`coding-countersign.md`: same shape, different lens. Looks for what the
judge missed.

`coding-notary.md`: no `allowed_tools: [read, bash]`, no write — pure
evidence-taking. Output is a file:line + commit-SHA dossier.

`coding-secretariat.md`: optional. Records all three audit outputs to
`.pi/audit-log/<YYYY-MM-DD>.jsonl`. Has `allowed_tools: [write]` only.

### B2 — Worker split + multi-phase

`coding-coder.md`:

```markdown
---
name: coding-coder
soul: ../souls/coding/_common.md
allowed_tools: [read, bash, edit]
phase_inputs: [plan, apply]
output_contract: coder-report
---
# Coder

You implement. Two phases per dispatch:

**Phase 1 — plan.** Read the request and the project. Output a numbered
task list (the "apply manifest") in your first message. Do not edit
files yet.

**Phase 2 — apply.** For each task in the manifest, make the edit, run
the relevant gate, report the result. End with a per-task status block.
```

`coding-fixer.md`:

```markdown
---
name: coding-fixer
soul: ../souls/coding/_common.md
allowed_tools: [read, bash, edit]
phase_inputs: [prerequisites, applied_diff, test_output]
output_contract: fixer-report
---
# Fixer

You finalize. Triggered when the coder's apply phase failed a gate or
when the user explicitly asks to "polish" / "fix lint" / "make tests
green". Required inputs:

- `prerequisites`: what the coder said it was going to do
- `applied_diff`: the diff the coder produced
- `test_output`: the failing gate output

Do not redesign. Do not refactor. Fix the smallest thing that makes the
gate pass.
```

## Out of scope (deferred)

- A2 *runtime enforcement*: requires upstream change to `Agent` tool
  (pi-subagents / pi-coding-agent) to accept `allowed_tools`. Tracked as
  a follow-up.
- A5 *framework-level bash hook*: ADR-0008 says seatbelt is documentation,
  not enforcement. Stay aligned.
- A4 *audit gate phase*: needs new gate phase schema + semantics.
  v0.6.0 ships the field; v0.7.x ships the phase.
- C1 *complete orchestrator removal*: v0.6.0 deprecates; v0.7.0 removes.
- New `video` / `research` / `design` / `music` role groups: untouched.
  The A套 mechanisms apply to any future group; the B套 changes are
  coding-group only.

## Versioning

- v0.6.0: ships this roadmap.
- v0.6.x: bug-fix-only patches against v0.6.0.
- v0.7.0: remove `coding-orchestrator` and `LEGACY_ROLE_ALIASES`
  shims. (Six-month deprecation window.)
