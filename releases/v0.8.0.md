# pi-rolecast v0.8.0

> Hardens the audit surface, finishes the v0.6.0/v0.7.0 legacy cutover, and adds the dispatch helpers workflow orchestrators need.

## TL;DR

Three slots shipped:

| Slot | Title | What |
|---|---|---|
| **F1** | Hard-delete legacy role-pack files | `coding-{implementer,reviewer,docs,orchestrator}.md` removed from `role-packs/coding/`. `LEGACY_ROLE_REDIRECTS` table removed from `src/profile_loader.ts` and `src/extension.ts`. Old role names continue to hard-fail at load time (carried over from v0.7.0 E3). |
| **F2** | Runtime narrowing coverage tests | Three integration-style tests for `enforceRoleNarrowing` in `tests/unit/test_runtime_hook.ts`. Documents the parallel-subagents-share-last-role limitation noted in `src/extension.ts:474-483`. |
| **F3** | Audit dispatch helpers + gate-runner verdict consumption | `src/audit_workflow.ts` gains `resolveAuditDispatchPlan`, `recordAuditVerdict`, `readAuditVerdicts`, `summarizeAuditVerdicts`. `src/gate_runner.ts` `PhaseResult` gains `audit_required`, `audit_plan`, `audit_verdict`; `runPhase` short-circuits on non-approved verdict summaries. |

## ⚠ BREAKING CHANGES

- **Legacy role-pack files hard-deleted.** Projects that forked `role-packs/coding/coding-{implementer,reviewer,docs,orchestrator}.md` must `git rm` them. The `deprecated_redirect` skip clause in `discoverRolePacks` is gone.
- **`LEGACY_ROLE_REDIRECTS` table removed.** The migration hints that v0.7.0's `parseProfile` consulted are now inlined as a hard-coded four-name check with the same successor / REMOVED semantics.
- **Hard-fail on legacy role names in bindings and contracts declarations** (carried over from v0.7.0 E3, preserved verbatim). v0.7.0 was a soft cutover; v0.8.0 hardens it.

## F1 — Legacy role-pack files

Files removed:

```
role-packs/coding/coding-implementer.md
role-packs/coding/coding-reviewer.md
role-packs/coding/coding-docs.md
role-packs/coding/coding-orchestrator.md
```

`src/profile_loader.ts` no longer skips role-pack files with `deprecated_redirect` in their frontmatter (the key was removed). `discoverRolePacks` parses only the active keys.

`src/extension.ts` no longer imports `LEGACY_ROLE_REDIRECTS`. The tool_call hook's legacy-name consult branch is replaced with an inlined four-name check that surfaces the same migration hint at dispatch time.

## F2 — Runtime narrowing coverage tests

The v0.6.0 D-slot added `enforceRoleNarrowing` to the tool_call hook but the helper was only smoke-tested. v0.8.0 adds three integration-style tests:

```typescript
test("F2: fresh session has unrestricted currentRole", ...);
test("F2: Agent dispatch sets currentRole to the dispatched subagent_type", ...);
test("F2: sequential dispatches track the last one (parallel subagents share last role)", ...);
```

The last test pins down the parallel-subagents-share-last-role limitation that's documented in the v0.6.0 docstring at `src/extension.ts:474-483`. pi's extension API does not expose a `subagent_end` event, so two back-to-back Agent dispatches leave `currentRole` pointing at the second one. The helper still does the right thing for sequential use; parallel use inherits the LAST dispatched role's restrictions.

## F3 — Audit dispatch helpers + gate-runner verdict consumption

v0.6.0 added the declarative surface (`audit_roles`, `audit_unresolved`) but left two questions unanswered:

1. how does the workflow get the dispatch plan?
2. how does the gate runner know the audit verdict?

v0.8.0 closes both.

### Dispatch plan (workflow → audit team)

```typescript
import { resolveAuditDispatchPlan } from "pi-rolecast/dist/audit_workflow.js";

const plan = resolveAuditDispatchPlan(profile, "review");
if (plan.unresolved.length > 0) {
    throw new Error(`audit_roles unresolved: ${plan.unresolved.join(", ")}`);
}
for (const dispatch of plan.dispatch) {
    await Agent({ subagent_type: dispatch.role, input: { model: dispatch.alias, ... } });
}
```

`AuditDispatch` carries `role`, `alias`, `model_id`, `channel_id`. The gate runner also emits `audit_required` + `audit_plan` on the `PhaseResult` so callers do not have to call `resolveAuditDispatchPlan` separately when they have the gate summary in hand.

### Verdict consumption (workflow → gate runner)

After dispatching the audit team, the workflow writes `<runDir>/audit-verdicts.json`:

```json
{
  "phase": "review",
  "verdicts": [
    { "role": "coding-judge",       "verdict": "approved" },
    { "role": "coding-countersign", "verdict": "needs_rework", "reason": "missing tests" }
  ]
}
```

The gate runner reads this file *before* attempting the phase commands. A summary of `rejected` or `needs_rework` short-circuits the phase to `status: "fail"` with `reason: "audit:<summary>"`.

Summary priority:

1. any `rejected` verdict → `"rejected"`
2. any `needs_rework` verdict → `"needs_rework"`
3. otherwise → `"approved"`

When the audit verdict summary is non-approved, `attempt: 0` is recorded on the `PhaseResult` so callers can distinguish audit-driven failures from command-driven ones.

### Recording verdicts

```typescript
import {
    recordAuditVerdict,
    type AuditVerdict,
    type Escalation,
} from "pi-rolecast/dist/audit_workflow.js";

const r = recordAuditVerdict(
    runDir,
    "coding-judge",
    "needs_rework" as AuditVerdict,
    profile.escalation as Escalation,
);
if (r.capReached) { /* permanent failure */ }
```

`approved` does NOT increment; `needs_rework` and `rejected` both do. The `capReached` flag is computed via `canResubmit` against the configured `escalation.audit_max_resubmits` cap.

## Migration (v0.7.0 → v0.8.0)

v0.7.0 was a stepping stone. Profiles already on v0.7.0 bindings (renamed to `coding-coder` / `coding-judge` / `coding-diarist`, with `coding-orchestrator` removed) only need to:

1. `git rm role-packs/coding/coding-{implementer,reviewer,docs,orchestrator}.md` if you forked them.
2. Adopt the v0.8.0 audit dispatch helpers if you wrote a workflow orchestrator that retries on audit rejection (otherwise the helpers are pure additions).

Profiles still on v0.6.0 names: apply the v0.7.0 rename first, then the v0.8.0 `git rm`. See `references/profile-schema.md` for the four-table rename.
